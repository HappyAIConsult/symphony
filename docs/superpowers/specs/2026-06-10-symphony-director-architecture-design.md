# Symphony-как-директор: архитектура knowledge + пайплайна (дизайн)

**Дата:** 2026-06-10
**Автор:** d.svrrt@outlook.com (через Claude Code)
**Статус:** черновик на ревью
**Связано с:** `2026-06-10-symphony-claude-integration-design.md` (движковая интеграция Claude), План 1 (реализован).

## 1. Цель и видение

Превратить Symphony из «агента-разработчика» в **агента-директора проекта**: он управляет работой, опираясь на накопленный контекст (knowledge), и на каждом шаге порождает **MD-артефакты** через **роли**. «Проект» — это **бизнес-единица**, которая может содержать несколько код-репозиториев (или монорепо с несколькими апп-ами) и собственный knowledge; knowledge местами кросс-проектный.

Среда зафиксирована: **чисто локально (WSL на этой машине), git на диске + GitHub как бэкап, solo, запуск под присутствием владельца.** Knowledge — **простые `.md` в git.**

## 2. Главный принцип: «через Symphony, не поверх»

Symphony **намеренно минимален** (подтверждено по SPEC §11.5, §7): оркестратор **только читает** трекер (кандидаты в активных статусах, рефреш статусов) и даёт агенту turn'ы. **Все записи** (смена статусов, комментарии, создание тикетов, `blockedBy`, PR-метаданные) делает **сам агент инструментами из промпта** (`linear_graphql` и др.). Понятия «роль» в Symphony **нет нигде** (проверено grep'ом по SPEC/WORKFLOW/коду/скиллам).

**Уровни (что где «зашито»):**

| Уровень | Что знает про пайплайн | Кто определяет |
|---|---|---|
| Движок Symphony | Ничего про роли/стадии/артефакты. Только: поллить `active_states`, давать turn'ы, читать статусы, стримить события. | OpenAI (фиксировано) |
| Linear | Имена статусов и тикеты. Не знает смысла статусов. | Владелец (UI Linear) |
| `WORKFLOW.md` front-matter (yaml) | Конфиг движка + **список** `active_states`/`terminal_states` (только имена). | Мы |
| `WORKFLOW.md` проза (markdown) | **Вся** логика пайплайна: статус→роль→артефакт, итерации, ожидание, когда заводить тикет. | Мы |
| Роли = файловые субагенты | Системные промпты ролей. | Мы |
| Артефакты MD (knowledge) | Долговечные выходы шагов. | Мы (агент пишет) |
| `project.yaml` | Манифест бизнес-единицы (репозитории, Linear, стек). | Мы |

Вывод: пайплайн — это «программа на прозе» (`WORKFLOW.md`) + файловые роли-субагенты + артефакты. Параллельный оркестратор не строим.

## 3. L0 — Топология на диске (knowledge-центричная)

Durable на диске = **engine + knowledge** («мозг» директора). Код **не** хранится постоянно — клонируется свежим на каждый тикет в эфемерный воркспейс; канон кода — на GitHub.

```
~/sym/
├── engine/                              # Symphony (форк HappyAIConsult/symphony)   [git]
├── knowledge/                           # ЕДИНЫЙ durable git-репо                          [git]
│   ├── global/                          #   кросс-проектное
│   │   ├── owner-profile.md             #     кто владелец, стиль, предпочтения
│   │   ├── methods/                     #     методики/плейбуки
│   │   └── glossary.md
│   ├── projects/<project>/              #   бизнес-единица
│   │   ├── project.yaml                 #     манифест (Linear, код-репо, стек) — §7
│   │   ├── overview.md                  #     что это, цели, north star
│   │   ├── status.md                    #     живой статус проекта (ведёт директор)
│   │   ├── decisions/NNNN-<slug>.md      #     ADR-лог
│   │   ├── retrospectives/YYYY-MM-DD.md
│   │   └── artifacts/<issue>/<NN>-<role>.md   # выходы шагов (§6)
│   ├── inbox/                           #   сырой втекающий контекст до дистилляции (§5)
│   │   └── telegram/YYYY-MM-DD/...
│   └── sym-plugin/                      #   Claude Code плагин: роли + скиллы (§6, §7)
│       ├── manifest.json
│       ├── agents/<role>.md             #     роли = файловые субагенты (system-prompt в теле)
│       └── skills/                      #     commit/push/pull/land и пр.
└── workspaces/                          # эфемерные клоны кода на тикет (Symphony workspace.root)
```

**Решения:** единый knowledge-репо (дробить — позже при росте); корень `~/sym/`; код локально постоянно НЕ держим (если владелец сам хакает код — это в его обычной папке, вне `~/sym/`).

## 4. L1 — Структура knowledge и конвенции

- Каждый MD имеет **frontmatter**: `project`, `type` (decision/retro/spec/artifact/research/scenarios/review/blocked/…), `status`, `source`, `date`, `links: [...]`.
- `decisions/` — нумерованные ADR (контекст → решение → последствия; включая «какие варианты пробовали/отвергли»).
- `artifacts/<issue>/<NN>-<role>.md` — выход каждого шага роли; следующий шаг **читает предыдущие** артефакты того же `<issue>` (отсюда «строятся друг на друге»).
- `status.md` — живой статус проекта (у Symphony проектного статуса нет — это чистое добавление).
- `inbox/` — куда падает сырьё; шаг «дистилляции» превращает его в структурированный knowledge.

## 5. L2 — Ingestion (Telegram + заметки → knowledge)

- **Заметки** уже `.md` в git — лежат прямо в knowledge.
- **Telegram**: агенту даётся **Telegram-инструмент** (MCP-сервер, по образцу нашего Linear-MCP) с операциями вида `telegram_search` / `telegram_send` / `telegram_poll`. Два режима:
  - **on-demand**: директор по ходу запрашивает релевантный контекст из Telegram;
  - **дистилляция**: периодически сырьё из Telegram падает в `inbox/telegram/`, отдельный шаг превращает в `decisions/`/`overview`/заметки.
- Telegram-инструмент — **отдельный мини-билд** (как `Claude.LinearMcp`), см. §8.

## 6. L3 — Пайплайн: статусы Linear ↔ роли-субагенты ↔ артефакты

**Модель:** один тикет проходит стадии через **статусы Linear**; на каждой стадии директор дёргает **роль-субагента**; каждый шаг пишет артефакт MD.

**Роли = файловые субагенты** в `knowledge/sym-plugin/agents/<role>.md` (frontmatter: name/description/tools/model; тело = system-prompt роли). Инжектятся в headless-сессию флагом **`--plugin-dir ~/sym/knowledge/sym-plugin`** (НЕ через хрупкий `--agents` JSON). Директор (верхняя сессия) вызывает их инструментом **Agent** (`subagent_type` = имя роли).

**Дефолтный пайплайн (статусы тюнятся в Linear + проза):**

| Статус Linear | Роль (субагент) | Обязательные артефакты | Дальше |
|---|---|---|---|
| `Backlog` | — | — | человек/директор |
| `Todo` | director | `00-brief.md`, правит `overview`/`status` | → Discovery |
| `Discovery` | analyst | `01a-research-current-state.md` (как СЕЙЧАС реализовано то, что трогаем), `01b-scenarios.md` (ВСЕ юзер-сценарии), `01c-analysis.md` (требования/критерии/риски) | → Design |
| `Design` | architect | `02-design.md` — **выводится из сценариев** (scenario-first), какие репо/аппы затронуты | → In Progress |
| `In Progress` | developer | код-PR + `03-impl-notes.md` | → Review |
| `Review` | reviewer/tech + reviewer/product | `04a-tech-review.md` (соответствие арх-принципам), `04b-product-review.md` (**интерфейс пользователя; покрыты ли ВСЕ требования по КАЖДОМУ сценарию**) | см. правило итерации |
| `Waiting` | director | `NN-blocked-<topic>.md` | сам, когда придёт ответ |
| `Human Review` | director | workpad + `status.md` | владелец |
| `Rework` | (возврат) | — | → Discovery/Design/In Progress |
| `Done` | director | `05-retro.md` + `retrospectives/` | — |

**Ваши добавления зашиты как ОБЯЗАТЕЛЬНЫЕ артефакты** (не отдельные статусы — доска чистая, rigor гарантируется требованием файла; любой шаг можно «повысить» до статуса-гейта позже):
- **Research текущего состояния** — `01a`, и проза: «Design ЗАПРЕЩЁН до research».
- **Сценарный центр** — `01b-scenarios.md`, и проза Design: «решения выводятся ИЗ сценариев».
- **Раздельное ревью** — `04a-tech` + `04b-product`; product-review смотрит реальный пользовательский интерфейс и проверяет покрытие всех требований по всем сценариям.

**Правило итерации (ревьюер вернул):** по каждому замечанию — *починить в рамках* → вернуть статус назад (In Progress/Design/Discovery); *вне scope* → `issueCreate` новый тикет (`related`/`blockedBy`). Обе ветки нативны (Rework + `linear_graphql`).

**Гранулярность turn'ов:** рекомендуется **одна стадия = один turn** (директор дёргает роль → пишет артефакт → двигает статус → выходит; следующий poll → следующая стадия). Прогресс виден на доске, есть чекпойнты, ложится на родную модель Symphony.

**Сценарий ожидания (Никита):** агент пишет `NN-blocked-<topic>.md` (что ждём, от кого, текст отправленного, с какого времени), обновляет workpad, ставит `Waiting`. В `Waiting` на каждом poll-тике дёшево проверяет Telegram-инструмент: нет ответа → сразу завершает turn; есть → фиксирует, возвращает прежний статус, продолжает. Повторные проверки даёт сам поллинг Symphony.

## 7. L4 — Привязка к движку

- **`project.yaml`** (в `knowledge/projects/<p>/`) — манифест бизнес-единицы (наш, не Symphony):
  ```yaml
  project:
    key: turbo-wedge
    name: Turbo Wedge
    linear: { team: HAP, project_slug: turbo-wedge-xxxx }
    repos:
      - { name: web, url: https://github.com/<you>/tw-web.git, default_branch: main, test: "pnpm test" }
      - { name: api, url: https://github.com/<you>/tw-api.git, default_branch: main, test: "mix test" }
    knowledge: projects/turbo-wedge
  ```
  Читают: хук `after_create` (какие репо клонировать), тулинг (генерация/параметризация per-project `WORKFLOW.md`), сам директор (репозитории/стек). Для одно-репо-проекта необязателен.
- **Per-project `WORKFLOW.<project>.md`** настраивает Symphony: `tracker.project_slug`, `agent.kind: claude`, секция `claude` (вкл. `plugin_dir`), `server`, и **проза пайплайна** (§6).
- **Knowledge монтируется через `--add-dir ~/sym/knowledge`** — агент пишет артефакты прямо в локальный knowledge-репо по реальному пути (клонировать не нужно). (Прим.: `--add-dir` даёт доступ к файлам, но НЕ к `.claude/`-конфигу — поэтому роли/скиллы доставляем плагином, см. ниже.)
- **Роли+скиллы — плагином через `--plugin-dir ~/sym/knowledge/sym-plugin`** (сессионно, файлово, без засорения `~/.claude`).
- **Два git-таргета:** код → PR в код-репо; артефакты → коммит/пуш в knowledge-репо. Проза WORKFLOW велит коммитить оба.
- **workpad-комментарий** = живой индекс со ссылками на файлы-артефакты и «на чём заблокированы».

## 8. Изменения в форке Symphony (что реально дописать в движок)

1. **`claude.plugin_dir`** (новое поле в секции `claude` схемы) → `Claude.AppServer` добавляет `--plugin-dir <dir>` в команду запуска. Так доставляются роли-субагенты и скиллы. (Заменяет идею хрупкого `--agents`.)
2. **`claude.add_dirs`** (опц., список) → `--add-dir` для монтирования knowledge в воркспейс.
3. **Telegram-инструмент агента**: новый MCP по образцу `Claude.LinearMcp` (`telegram_*`-операции) + проброс в `--mcp-config`/`allowed_tools`. Отдельный мини-проект.
4. Всё под `agent.kind: claude`; Codex-путь не трогаем.

## 9. Что в Symphony НЕ трогаем (границы)

- Оркестратор остаётся scheduler+reader (§11.5). Никакой пайплайн/роли в движок не зашиваем.
- `.codex/*` и `Codex.AppServer` — для Codex-бэкенда.
- Не вводим понятие «роль» в движок — роли живут как файловые субагенты.

## 9a. Инварианты (жёсткие правила — без двусмысленности)

Источник правды: `knowledge/global/methods/governance.md` (читается ролями).

1. **Разделение код/документы:** код-репозиторий = ТОЛЬКО код; все документы,
   артефакты, решения, ретро — ТОЛЬКО в knowledge. В код документы не кладём.
   Локальная копия кода не нужна (канон — GitHub, агент клонирует эфемерно).
2. **Сохранность:** артефакты пишутся в durable knowledge (не в эфемерный
   воркспейс); директор после этапа коммитит+пушит knowledge → ничего не теряется.
3. **Цепочка:** каждый этап ОБЯЗАН прочитать все артефакты предыдущих этапов того
   же `<issue>` и опираться на них; чужие не удалять/не перезаписывать; порядковые
   префиксы сохраняют порядок и историю.

Закреплено в: `governance.md`, во всех `sym-plugin/agents/*.md`, в `pipeline.md`.

## 10. Вне объёма / декомпозиция на планы

Это несколько независимых подсистем — реализуется отдельными планами (каждый — рабочий и тестируемый сам по себе):

- **План A — Knowledge-каркас:** структура `~/sym/`, knowledge-репо, `project.yaml`, `sym-plugin` (skeleton: manifest + перенос скиллов из `.claude/skills`).
- **План B — Роли-субагенты + движковый инжект:** `claude.plugin_dir`/`add_dirs` в схему + `Claude.AppServer`; набор `agents/<role>.md` (director/analyst/architect/developer/reviewer.tech/reviewer.product); тесты.
- **План C — Пайплайн-проза:** `WORKFLOW.<project>.md` с таблицей §6, правилами итерации, протоколом ожидания.
- **План D — Telegram-инструмент:** `Claude.TelegramMcp` (+ эндпоинт), проброс агенту; протокол ожидания.
- **План E — Ingestion/дистилляция:** `inbox/` + шаг дистилляции (роль).

Порядок: A → B → C → (D, E по необходимости). Smoke-тест движка (dogfood) можно прогнать уже на текущем Плане 1 — независимо.

## 11. Открытые вопросы / риски

- **Конкурентность при общем knowledge-репо:** при `max_concurrent_agents > 1` параллельные коммиты в один knowledge-репо требуют аккуратности (per-issue ветка/rebase, или сериализация). На старте — `1`.
- **Telegram MCP:** какие именно чаты/каналы мониторим; формат «ожидаемого ответа» (как агент уверенно определяет, что пришёл нужный ответ).
- **Стоимость turn'ов** в `Waiting` (частый дешёвый поллинг) — настроить интервал/лимиты под подписку.
- **Точный набор статусов** правится в Linear + прозе; добавления §6 — артефакты, при желании повышаются до статусов-гейтов.
- Генерация `WORKFLOW.<project>.md` из `project.yaml` — ручная или скриптом (решим в Плане C).
